# 用 TypeScript 复刻 Minecraft（v10.2.1）：生成提速

> 本文是 mc-replica 系列的第 v10.2.1 篇。v10.2 让每个原型、装饰在整个游戏里只算一次；这一版让单个原型、装饰本身变快。
> 改了三处：含水层的格子状态跨区块共享、周围一样时直接返回空气、查生物群系时先看近的。
> 同样 81 个区块，总时间从 45.4 秒降到 35.3 秒（−22%），生成结果逐格不变。
> 开发日志见 [../notes/v10.2.1-notes.md](../notes/v10.2.1-notes.md)。

## 二、先采样

`node --cpu-prof` 的结果（v10.2 的流程）：

- **原型占 52%**：含水层 `computeSubstance` 自身耗时 12.6%，是单个函数里最高的；密度函数和噪声加起来约 30%。
- **装饰占 28%**：其中一半在查生物群系。
- `Climate.build` 占 5%，是每个 Worker 启动时建一次参数表，不是每个区块的成本。

## 三、含水层

### 原版怎么决定一个空格子是空气、水还是岩浆

v3 的文章讲过：世界按 16×12×16 分成格子，每个格子里随机放一个中心点，每个中心点有自己的“含水层”（水位和流体）。
一个空着的方块，找周围 2×3×2 = 12 个格子里最近的 4 个中心点：

- 最近的比第二近的近得多：直接听最近的那个；
- 夹在两个含水层之间：算“压力”，压力大的地方变成石头墙（两块水之间的那道墙）。

每个空方块都要做一遍，包括地面以上的天空。

### 先试了两个小改动

**记住 12 个格子的下标**：相邻的方块几乎总是同一组格子，换组时才重新查。只快了 3%：查下标本来就不贵。

**周围一样时直接返回空气**：如果 12 个格子的含水层水位和流体都一样，两两之间的压力是 0（水位差为 0），不会变成墙。
这时在水位以上的方块，原版算出来一定是空气：

```ts
// 捷径：12 个格子的含水层完全一样、这里又在水位以上时，下面不管哪几个格子最近，结果都是空气
if (j >= this.nearAirFrom) {
  this.shouldScheduleFluidUpdate = false
  return Fluid.air
}
```

为什么只在“空气”时走捷径？原版还会算一个“要不要安排流体更新”的标记，它的阈值 `FLOWING_UPDATE_SIMILARITY` 是负数（−0.76），
所以就算周围都一样，这个标记也还和距离有关。好在这个标记只在结果是水或岩浆时才用得上，空气用不到。这一步也只快了一点。

### 真正的大头：算水位

再采样一次，`computeFluid`（算一个格子的水位）占了原型的 30%。算一个格子的水位要求好几个大的密度函数：

- 附近 13 列的“预估地表高度”（有缓存）；
- erosion 和 depth：判断是不是深暗之域，不放水；
- floodedness、spread：决定是淹没、随机水位还是干的。

一个区块的方块会用到周围 3×3 列格子，大部分和邻居区块是同一批格子，但每个区块都自己从头算一遍。

### 能不能跨区块缓存

格子中心点的位置是 `random.at(gx, gy, gz)`，和区块无关。问题在 erosion 和 depth：原版是在区块的 NoiseChunk 里求值的，
里面的 `flat_cache` 在**区块范围内**按 quart 取值（x、z 对齐到 4 的倍数，y 取 0），**范围外**按精确位置取值。
我们在 v3 用 `chunkLocal()` 照搬了这个规则。所以同一个格子，从不同的区块看，erosion 可能差一点点。

但这个“差一点”只取决于一个是非：**格子中心点在不在当前区块的 flat_cache 范围里**。所以缓存的键加上这一位就行：

```ts
const qx = Math.floor(this.locX[c] / 4) - shared.qx0
const qz = Math.floor(this.locZ[c] / 4) - shared.qz0
const inside = qx >= 0 && qz >= 0 && qx <= 4 && qz <= 4 ? 1 : 0
const key = (((gx + 0x200000) * 0x400000 + (gz + 0x200000)) * 128 + (gy + 64)) * 2 + inside
```

缓存挂在 Worldgen 上（每个 Worker 一份），按 noise_settings 分开。相邻 7×7 个区块的原型从 83.6 ms 降到 63.9 ms。

## 四、查生物群系

装饰时要在区块整个高度上查群系（矿石从基岩放到山顶），一个区块大约 1500 个 quart。原版也是这么多，数量减不下来，只能让每次查得更快。

查群系是在 7593 项的气候参数表里找“最近”的一项。v4 建了一棵树：把表项按某一维分组装进盒子，算目标到盒子的距离下界，比当前最好的还远就整个跳过。

原来是按固定顺序访问子盒子。改成**按距离下界从近到远**：先找到近的，后面能剪掉的更多。

```ts
// 子盒子入栈，按下界从大到小排好（插入排序），栈顶是最近的
for (const c of node.children!) {
  const lb = this.lowerBound(c)
  if (lb > best) continue
  let k = sp++
  while (k > base && lbs[k - 1] < lb) { nodes[k] = nodes[k - 1]; lbs[k] = lbs[k - 1]; k-- }
  nodes[k] = c
  lbs[k] = lb
}
```

结果会不会变？找的是“距离最小，一样近时取表里靠前的”，这个答案和访问顺序无关；剪枝用的是 `>` 而不是 `>=`，一样近的候选不会被剪掉。

## 五、怎么证明结果没变

每一步都用两种方法核对：

1. **前后校验和**：主世界、下界、末地各生成 25 个完整区块（含地物、颜色），和改之前的版本比 SHA-1，全部相同。
2. **新测试**（`tests/fast-paths.test.ts`）：
   - 含水层：两个 Worldgen，一个关掉提速（`fastAquifer = false`），生成 (0, 0) 周围 3×3 个区块的原型，逐格相同；
   - 查群系：2 万个随机点和逐项比较的结果相同，其中四分之一取在参数区间的端点上，最容易出现一样近的情况。

为了确认测试真能发现问题，我故意把剪枝改成 `>=`，查群系的测试马上失败。

也有测不出来的：把含水层缓存键里“在不在范围里”那一位去掉，这 9 个区块的结果也没变。这一位理论上是需要的，所以保留；但这个测试证明不了它。
