- 矿石（含矿脉）、所有树和巨型蘑菇、积雪和冰

## 过程

1. **原版对照存档**：用你下载的 1.21.4 server.jar 在我这边无界面跑服务端（种子 42、关结构、`pause-when-empty-seconds=-1`，
   否则空服 60 秒后暂停，后面的 forceload 区块不会生成），`forceload add` 生成指定区域，再用 `tools/vanilla/anvil.ts` 读存档。
   - 关掉地物和雕刻器的存档：v0~v4 的地形 + 地表和原版逐格一致（出生点 99.996%，差的 58 格是流动的水；其他 3 个区域 100%）
   - 唯一的系统差别是凝灰岩 / 铁矿 → 矿脉，接着就做了，做完 100%
2. **矿脉**：NoiseChunk 加 `wrap()`，让 vein_toggle 等和 final_density 走同一套插值。
3. **地物框架**：`feature/core.ts`（世界接口、IntProvider、HeightProvider、方块提供者、RuleTest、BlockPredicate）、
   `placement.ts`（修饰器，按 Java Stream 的深度优先顺序消耗随机数）、`features.ts`（矿石、圆盘、积雪、巨型蘑菇、选择器）、
   `tree.ts`、`decorate.ts`（FeatureSorter + applyBiomeDecoration）、`worker/pipeline.ts`（原型 / 装饰缓存）。
4. **对照用的数据包**：只留矿石的、只放树的（每个区块从 36 种树里随机一种），原版和我们用同一个数据包，
   地物序号和种子都对得上，可以单独核对一类地物。脚本：`tests/featurePacks.ts`（TS）和生成原版存档时的同款 Python。
5. **找到的错**：
   - 放置修饰器一开始“先算完所有位置再放”，矿石形状全错 → 改成递归，和 Stream 一样交错消耗随机数
   - 樱花树的 `branch_start_offset_from_top` 是不带 type 的 UniformInt → IntProvider 兼容这种写法
   - 红树的根：`nextBoolean() ? 旁边 : 旁边的下面` 应该是 `? 旁边 : 下面` —— 在 server.jar 里用字符串找到混淆后的类，`javap -c` 看字节码确认
   - `Mth.sin` 以为 1.21.2 起是 double 参数，字节码显示 1.21.4 还是 float
6. **区块之间的顺序**：原版后装饰的区块能看到先装饰的邻居放下的树。实验（雪原针叶林 4 个区块的树方块）：
   每个区块只看原型 45%，共享世界按“先 z 后 x”依次装饰 92.5%，倒过来 40%。
   最后用 4×4 区块的“装饰区域”：区域内按顺序共享、区域之间只看原型，结果和加载顺序无关，90.6%。
   Worker 按区域固定分配（`pool.call(..., affinity)`），缓存才能复用。
7. **性能**：
   - 没实现的地物整个跳过（包括它的放置修饰器）：每个区块的地物时间 404 → 71 ms
   - 群系参数表建成包围盒树：一次查找 160 → 26 µs，和逐项比较的结果完全一样（含平局，2 万个点对照）
8. **渲染**：树叶按原版“流畅”画质画成不透明的完整方块；雪层（2/16）、地毯（1/16）是扁盒子；
   藤蔓、可可果、苍白垂须、胎生苗是十字形镂空（着色器里 alpha < 0.5 丢弃）。

## 实测数据

| 项目 | 数值 |
| --- | --- |
| 地形 + 地表 + 矿脉（关掉地物的存档，4 个区域 64 个区块） | 99.996% ~ 100% 一致 |
| 只留矿石：36 个区块 | 16 个区块的矿石逐格一致（5300 块）；其余差在区块边上（生成顺序） |
| 只放树：21 个群系样本 + 出生点 | 75 个区块逐格一致（8500 多块）；不一致的只有苍白橡树（苔藓地块没实现） |
| 完整装饰，出生点 16 个区块（含没实现的地物） | 99.47% 的方块一致 |
| 区块原型 / 装饰（Node，未打包） | 约 130 ms / 约 70 ms |
| 测试 | 80 个，全部通过（有原版数据和报告时） |
